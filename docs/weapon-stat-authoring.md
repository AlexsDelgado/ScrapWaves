# Weapon stat authoring

Tune a `WeaponData` asset in its Inspector. Existing manually balanced values remain the baseline. This workflow does not import the historical balance sheet or apply its numbers.

1. Select the weapon asset used by the scene or loadout. Sandbox copies and production assets are separate; confirm the asset reference before editing.
2. Under **Level and mode**, select Basic level 1–5 or independent A/B level 6–10, then Automatic, Manual, or Q ability.
3. If the selected key has no row, choose **Add overrides for this level and path**. New controls begin as **Inherit**.
4. Enable only the value you want to set. An enabled value replaces that exact weapon/level/path value before the documented player and heat modifiers. Mode values are independent; shared critical controls apply across eligible modes of the selected row.
5. Read **Preview – neutral player / zero heat** and **Resolved gameplay: neutral player, zero heat**. The latter uses gameplay diagnostics with player multipliers 1x, crit chance 0%, crit severity 2x and heat 0%. It observes values without firing, spending ammo, advancing timers or saving assets. It does not prove collision behavior or show a heated/item-equipped scenario.
6. Review nearby levels, the opposite path and other modes. Save deliberately; normal Unity Undo/Redo applies. Switching Inspector context preserves hidden data.

Each row is an exact key, not an accumulated upgrade. A6 does not add level 5 again, and B7 does not borrow A7. Turning a value back to **Inherit** retains its stored number while restoring the current legacy source. **Shared weapon tuning (all levels)** changes the source for every row that inherits it; **Selected progression source** exposes the relevant legacy progression values. Use these broader sources deliberately.

Read each field's displayed unit and scope. Distances are meters; radii are not diameters; rotation is rotations/second; attack cadence is distinct from projectile count and spacing. UI critical chance is a percentage backed by a 0–1 fraction. Counts marked “total” include the first target/explosion. Damage, generic range and attack rate require positive values; legal zero values are explicit controls, not missing data. Validation errors must be resolved before using the profile.

Several mechanics have separate controls:

- Rocket acquisition, flight distance, projectile lifetime and blast radius are independent. Authored automatic flight distance measures the arc. B Q children have their own geometry and lifetime. A shorter lifetime can end a flight before its distance limit.
- Mortar A ordinary attacks use child landing spread, not a parent blast radius. A is Grapeshot; B is Multi-Charged. Mortar critical hits remain off until **Enable critical hits** is set for the exact row.
- Flame contact puddles include target-contact puddles generated by Q. Central Q puddles have separate radius/lifetime controls. Inherited tick clocks keep their baseline behavior; an explicitly set rate uses player attack speed and the automatic overheat ratio, with a 100-Hz neutral limit. Emission timing is separate.
- Blade orbit radius, contact radius, slash reach, thrust length and dash range are distinct. A Manual-row reach override does not change Q reach; inherited Q still retains its old global range source.
- Q ammo cost and Q cooldown are independent of Manual capacity and attack cadence. Cannon A inherits its existing 80-ammo Q cost unless that exact row overrides it. Existing path-capacity player-scaling rules are retained.

To scaffold all 15 progression keys without changing numeric tuning, select the intended `WeaponData` assets and run **Tools > ScrapWaves > Weapon Stats > Preview Selected Weapon Migration**. Review the Console's asset identity, hash and missing-row count. **Add Inherited Rows to Selected Weapons** then adds only missing disabled rows, supports Undo, and does not save automatically. Existing authored or hidden rows remain intact. Invalid/unknown-version profiles fail rather than being rewritten.

For a manual check, open `Assets/Scenes/Testing/WeaponTestingSandbox.unity`, confirm the referenced weapon asset, enter Play mode and use the existing sandbox loadout/level/path controls. F1 toggles UI-mouse mode. Inspect the player's `DebugMonitor` and the visible aim/geometry feedback. Start neutral, change one control, and measure real HP loss, hit boundary, projectile count, elapsed time or ammo use. Then test an unrelated mode, both paths, level 5 -> 6, a player bonus, relevant heat thresholds, repeated Q, switching/reload and delayed hits after switching. Compare diagnostics, HUD, upgrade preview and VFX with the observed result. Avoid treating a getter value as gameplay proof.

The **Validate Authoring and Consumers**, **Compile Player Scripts** and **Build Windows Player** menu items are under **Tools > ScrapWaves > Weapon Stats**. Their resulting reports, not this guide, determine pass/fail. The complete 72 source concepts and additional controls are tracked in [weapon-stat-traceability.csv](weapon-stat-traceability.csv) and [weapon-stat-additional-controls.csv](weapon-stat-additional-controls.csv).

Unused Flame cone/stream-duration values, legacy Mortar shell-count/cone data, and old balance-row `Scaling`/`Effectiveness` metadata are retained without being presented as working gameplay controls. Partial player effectiveness (`1 + effectiveness × (player multiplier − 1)`) is an unapplied proposal from the approved plan that still requires a design decision; current live player composition is preserved. See [shared runtime contracts](weapon-stat-shared-runtime-contract.md).
